## 開発ルール

### 実装前の確認（最重要）

- **実装・ドキュメント変更・ルール更新を問わず、必ず「検討結果の報告 → 確認 → 実作業」の順を守る**
  - 分析・提案の依頼を受けた場合も同様。検討結果のみ先に報告し、承認を得てからファイル操作に入る
  - 非自明な選択肢がある場合は比較表を出す
  - ユーザーに確認するのは「方針・アプローチの選択」のみ。バージョン番号・設定値などの細部はこちらで調査して決める

### コード変更後の確認

- コード変更後はテスト（プロジェクトに応じたコマンド）を実行し、全件PASSを確認してから提示する
- ビルド・デプロイはユーザーから依頼された時のみ実行する

### UI編集（UIを含むプロジェクトの場合）

- UI変更前に、変更対象を含む**親コンポーネントのファイル全体**を読む
- サイズ・レイアウトに影響する変更は、変更前後の構造をテキストで明示してから確認を求める
- 各スプリントで動作確認可能な状態を維持する。フルデザイン変更は独立タスクで行う

### 往復数の計測

開発速度の改善に使うため、タスクごとの往復数を記録する。

- **定義:** ユーザーメッセージ → Claude応答 = 1往復
- **計測範囲:** タスク着手から ✅ になるまでの全往復数。Sprintレビューで指摘を受けて追加対応した往復もそのタスクに加算する
- **記録場所:** `tasks/task-list.md` の `往復数` 列に記入する
- **振り返り:** Sprint振り返りに往復数サマリーを含める。5往復以上のタスクは原因を分析する

### Sprint完了時の必須手順

1. `tasks/task-list.md` の当該スプリント全タスクを ✅ に更新し、`往復数` 列を記入する
2. `memory/project_*.md` の進捗表を更新
3. 仕様変更があった場合: 対応するUC/ACファイルを更新
4. 解決済みの `knowledge-base.md` 項目を更新
5. **振り返りを実施し `tasks/retrospective-YYYY-MM-DD-SprintX.md` に保存**
   - ① 良かった点、② 問題になった点と再発防止策、③ ルール変更提案
   - ④ 往復数サマリー（スプリント平均・5往復以上のタスクと原因）
6. 動作確認（実機・ブラウザ等）で受入条件を手動検証
7. 「Sprint X 完了です」と報告

### 仕様変更の管理

- 仕様変更は既存文書を黙って上書きせず、変更内容を会話で確認してから反映する
- 変更が発生したらtask-list.mdのコメント記入とUCファイル更新を同時に行う

## カスタマイズガイド

### プロジェクト種別ごとの調整

| プロジェクト種別 | CLAUDE.md の追記事項 |
|---|---|
| Androidアプリ | ビルドコマンド（`./gradlew test` / `buildCMakeDebug`）、実機機種名、minSdk |
| Webフロントエンド | フレームワーク（React/Vue等）、テストコマンド（`npm test`）、ブラウザ確認手順 |
| バックエンドAPI | テストコマンド、DBマイグレーション確認、APIドキュメント更新ルール |
| C++/ネイティブ | ヘッダー事前確認ルール（API使用前にヘッダーをGrep/Readで確認） |

### Windows環境での追記事項（該当する場合）

CLAUDE.mdの末尾に以下を追加してください:

```
## Windows環境でのCLIツール実行

- JDKツール（keytool等）は文字化けを防ぐため非対話モードで実行する（全パラメーターをCLIに指定）
- bashでのパス指定は `/c/Program Files/...` 形式を使う
- 対話入力が必要なコマンドはPowerShellで実行する
```

### チームで使う場合

- CLAUDE.md はgitリポジトリにコミットしてチーム全員が同じルールで使えるようにする
- Constitution.md の品質制約と開発原則はチームで合意してから記入する
- ADRはアーキテクチャ上の決定をレビューしたエンジニアが承認してからstatusを「確定」に更新する
