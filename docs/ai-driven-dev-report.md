# AIドリブン仕様駆動開発 — 開発方針レポート

> 対象読者: Claude（AIアシスタント）を使った開発に初めて触れる方  
> 作成日: 2026-04-26  
> プロジェクト: PocketDJ（Android / Kotlin + C++）

---

## 1. はじめに ― Claudeとは何か

**Claude** は、Anthropic社が開発したAIアシスタントです。文章の作成・コードの生成・設計の相談など幅広い作業を自然言語（日本語・英語）で依頼できます。

このプロジェクトでは **Claude Code**（CLIツール版のClaude）を使い、AndroidアプリのフルスタックをAIと協働で開発しました。AIは「一緒に働くエンジニア」として機能し、人間は「プロダクトオーナー兼レビュアー」として意思決定を担います。

---

## 2. 開発フロー ― 全体像

この開発手法を **「仕様駆動開発 × AI協働」** と呼びます。コードを書く前に仕様を固め、その仕様に基づいてAIにコードを生成させる流れです。

```
① Constitution（憲法）
       ↓
② Specify（仕様化）
       ↓
③ Plan（設計・意思決定）
       ↓
④ Tasks（タスク分解）
       ↓
⑤ Implement（実装）← スプリント単位で繰り返す
       ↓
⑥ 振り返り（レトロスペクティブ）
       ↓
   次のスプリントへ
```

---

### ステップ① Constitution（憲法）― 開発のルールブックを作る

**Constitution.md** というファイルをプロジェクト最初に作成します。これはプロジェクト期間中に変更しない「憲法」です。

記載する内容:
- **スコープ**: 何を作るか・何を作らないかの明確な境界線
- **品質制約**: 数値目標（例: 音声レイテンシ20ms以下、クラッシュ率1%以下）
- **開発原則**: 「仕様駆動」「人間が最終判断する」「小さなタスク単位で進める」

**なぜ重要か**: AIは「言われたことは何でもやろうとする」性質があります。スコープが曖昧だと機能が際限なく膨らんだり、品質基準が不明確なまま進んでしまいます。憲法があることで「これは作らない」「これはこの品質でなければならない」という判断軸が固定されます。

---

### ステップ② Specify（仕様化）― 何を作るかを文書化する

実装に入る前に、**ユースケース（UC）** と **受入条件（AC）** を文書として作成します。

**ユースケース（UC）の例（EQイコライザー機能）:**
```
事前条件: トラックがデッキにロード済み
基本フロー:
  1. ユーザーがEQロータリーノブを回す
  2. システムがリアルタイムに音声フィルターを適用（20ms以下）
  3. ノブの回転角度が視覚的にフィードバックされる
代替フロー:
  - ノブをダブルタップ → 0dBにリセット
  - ノブを最小まで回す → 完全カット（Kill）
```

**受入条件（AC）の例:**
```
Given: デッキAで楽曲が再生中
When: Highノブを最小まで下げる
Then: 高音域が完全にカットされる（Killモード）
```

**なぜ重要か**: AIは仕様が曖昧だと「それっぽいもの」を作ります。受入条件まで書くことで、「何が完成とみなされるか」がAIにも人間にも明確になります。また、後からバグが出たときに「仕様通りか否か」を判断する基準になります。

---

### ステップ③ Plan（ADR）― 技術的な意思決定を記録する

**ADR（Architecture Decision Record）** は「なぜこの技術を選んだか」を記録するドキュメントです。

```
ADR-001: 音声API選定
  選択肢A: Oboe（推奨） — レイテンシ20ms以下を達成できる
  選択肢B: AudioTrack — レイテンシが高い、却下
  決定: Oboe採用
```

**なぜ重要か**: 数ヶ月後に「なんでこのライブラリを使ったんだっけ？」という疑問が生じたとき、AIはその経緯を覚えていません。ADRがあれば、AIが「ADR-001を参照してください」と案内できます。

---

### ステップ④ Tasks（タスク分解）― 30分単位に切る

機能ごとにタスクを分解し、**task-list.md** で管理します。

```
Sprint 5: イコライザー（UC-005）
  T-501: C++ EqProcessorを実装           ✅
  T-502: JNIブリッジにEQ操作を追加        ✅
  T-503: EqualizerUseCaseを実装           ✅
  T-504: ViewModelにEQ状態管理を追加      ✅
  T-505: EQロータリーノブUIを実装         ✅
  T-506: EqualizerUseCase単体テスト       ✅
  T-507: 実機検証（Pixel 8 Pro）          ✅
```

**ルール: 1タスク = 30分でレビューできる粒度**

**なぜ重要か**: AIは一度に大きな変更を生成できますが、「大きな変更」はレビューが困難でバグの温床になります。小さな単位に切ることで、各ステップで「意図した通りに実装されているか」を人間が確認できます。

---

### ステップ⑤ Implement（実装）― サンドイッチ構造

```
人間が方針を指示
      ↓
AIがコードを生成
      ↓
人間がレビュー・承認
      ↓
次のタスクへ
```

AIへの指示例:
```
「UC-005に基づき、EqualizerUseCaseを実装してください。
 AudioEngineRepositoryを通じてEQ操作を行い、
 High/Mid/Low の3バンドをそれぞれ独立して制御できるようにしてください」
```

**なぜ重要か**: AIに丸投げすると、仕様と異なる実装が生まれることがあります。「人間が方針を指示 → AIが実装 → 人間がレビュー」のサンドイッチ構造を守ることで、最終的な判断権が常に人間に残ります。

---

### ステップ⑥ 振り返り（レトロスペクティブ）― 毎スプリント改善する

各スプリント完了後に振り返りを実施し、**retrospective-YYYY-MM-DD-SprintX.md** として記録します。

```
良かった点: 
  - T-802・T-805を1セッションで完走できた
  
問題になった点:
  - Oboe APIの名前を確認せず実装し、ビルドエラーが発生（2時間ロス）
  
ルール改善:
  - 今後はC++ APIを使う前にヘッダーファイルを確認する
```

改善点はすぐにルールとして記録し、次のスプリントから反映します。

## 3. 気をつけるべきこと

### 注意点① AIには目がない

AIはコードを読み書きできますが、**画面がどう見えるかを確認できません**。

特にUI（画面のレイアウト）の編集では、コンポーネントの配置が崩れても気づかずに「実装完了」と報告してしまうことがあります。このプロジェクトでは、EQのスライダーをロータリーノブに変更したとき、`weight(1f)` というサイズ指定を追加した結果として再生ボタンが画面外に押し出されてしまう問題が発生しました。

**対策:**
- UI変更を依頼するときは「レイアウトの構造をテキストで先に示してから実装してください」と指示する
- 必ず実機またはエミュレータで見た目を確認する

---

### 注意点② 「やってしまった後」では遅い

AIは指示があれば何でも実装しようとします。**承認前に実装が始まってしまうと、修正のコストが発生します。**

このプロジェクトでは「実装前に複数案を比較提示 → 人間が確認 → 実装」というルールを設けています。

**対策:**
- 依頼するときは「まず提案だけしてください」「実装前に確認させてください」と明示する
- AIに方針を先に報告させ、OKを出してから作業に入らせる

---

### 注意点③ AIの記憶はセッションをまたがない

AIは会話セッションが終わると、原則としてその内容を覚えていません。翌日に「昨日の続きをやって」と言っても、前回の会話が記憶にない状態からスタートします。

**対策:**
- **CLAUDE.md** をプロジェクトルートに置く（Claude Codeがセッション開始時に自動読み込み）
- **memory/** フォルダに進捗・ルール・技術的決定を記録する
- この2つにより、新しいセッションでも「前回の続き」から始められる

---

### 注意点④ 仕様と実装がずれていく

開発を進めると「やっぱりこの機能の仕様を変えよう」という判断が生まれます。このとき、**コードは変わっても仕様書が更新されない**という問題が起きやすいです。

このプロジェクトでは、EQのスライダー→ロータリーノブへの変更がUCファイルに反映されないまま数スプリント経過してしまいました。

**対策:**
- 仕様を変更したら、その場でUCファイルも更新する
- スプリント完了チェックリストに「仕様書の更新確認」を含める

---

## 4. 強い点・利点

### 利点① 大量のコード生成を高速に行える

Clean Architecture（4層構造）に基づいたAndroidアプリでは、1機能を追加するだけで以下のファイルを作る必要があります:

```
C++実装 → JNIブリッジ → DataSource → Repository → UseCase → ViewModel → UI
```

これを人間1人で書くと半日〜1日かかることがありますが、AIを使うと**1セッション（数時間）でスプリント1本分（7〜11タスク）を完走**できました。

---

### 利点② アーキテクチャの一貫性が保てる

「UseCase名は仕様書のUC-IDと1対1対応させる」「Repository InterfaceはDomain層に置く」といったルールを最初に定めてAIに伝えると、AIはすべてのコードをそのルールに従って生成します。

人間だけで開発する場合、時間が経つにつれてルールが崩れることがありますが、AIは毎回同じルールで一貫したコードを出します。

---

### 利点③ 設計上の選択肢の検討が速い

「音声APIはOboeにするかAudioTrackにするか」「BPM検出はTarsosDSPにするかaubioにするか」といった技術選定を、AIは調査・比較表作成・推奨まで短時間で行えます。人間はその比較表を見て判断するだけでよく、**調査コストが大幅に削減**されます。

---

### 利点④ エラーの原因究明が速い

ビルドエラーや実行時エラーが発生したとき、エラーログをAIに渡すと**根本原因の特定と修正案の提示**を素早く行えます。

このプロジェクトでは、Java 24とOboeライブラリの非互換問題（Prefabが動かない）という難解な問題を、AIが類似事例と原因を調べて「`add_subdirectory`方式に切り替える」という解決策を提示しました。

---

### 利点⑤ ドキュメントの自動整備

通常の開発ではドキュメント作成が後回しになりがちですが、AIは「実装と同時にADRを書く」「知見が生まれたらknowledge-base.mdに追記する」といった作業を自然に行います。開発終了時点でドキュメントが整っている状態になります。

---

## 5. 工夫している点

### 工夫① CLAUDE.md + memory/ の二層記憶構造

AIの記憶を2つの場所で管理しています。

```
CLAUDE.md（プロジェクトリポジトリ内）
  → 開発ルール・禁止事項・ファイル構成ガイド
  → git管理対象。人間が読み書きできる
  → セッション開始時にClaudeが自動読み込み

memory/（Claude専用フォルダ）
  → Sprint進捗・技術的決定の累積記録
  → セッション間の継続性のために使用
  → feedback_*.md: 過去の失敗から学んだルール集
```

「同じ失敗を二度繰り返さない」ためにfeedback_*.mdを活用しています。例えば `feedback_android_build.md` には「Java 24はPrefabと非互換、`add_subdirectory`方式を使え」という知見が記録されており、次のAndroidプロジェクトでも参照できます。

---

### 工夫② スプリント完了チェックリスト

スプリント完了時に必ず実行する手順をチェックリスト化しています。

```
1. task-list.md の全タスクを ✅ に更新
2. memory/project_*.md の進捗表を更新
3. 仕様変更があれば UC/AC ファイルを更新
4. 解決済みの knowledge-base.md 項目を更新
5. 振り返りを retrospective-*.md に保存
6. 実機（Pixel 8 Pro）で受入条件を手動検証
7. 「Sprint X 完了です」と報告
```

このチェックリストを守ることで、「ドキュメントが実態と乖離する」「実機検証を忘れる」「振り返りが形骸化する」といった問題を防いでいます。

---

### 工夫③ UI変更前のレイアウト構造可視化

UI編集でコンポーネントが消えたり重なったりする問題が繰り返し発生したため、以下のルールを設けました。

```
UI変更前に:
  1. 変更対象の親コンポーネントのファイル全体を読む
  2. 変更前後のレイアウト構造をテキストで明示する
     例: 「変更後: Column > Row(weight:1f) > [EQノブ | Pitchスライダー]」
  3. 確認を得てから実装する
```

AIは「コードを変えると画面がどう変わるか」を視覚的に確認できないため、**テキストでレイアウト構造を事前に合意する**ことで画面崩れを防いでいます。

---

### 工夫④ 承認フローの徹底

AIは「すぐ実装したがる」性質があります。このプロジェクトでは以下の順序を徹底しています。

```
依頼を受ける
  ↓
検討結果・複数案を報告する（実装はしない）
  ↓
人間が方針を選択・承認する
  ↓
実装に入る
```

分析や提案を依頼された場合も同様で、「分析結果を報告してからファイルを変更する」ルールを設けています。

---

### 工夫⑤ 環境固有の落とし穴を記録する

Windows + bash環境でkeytool（Javaのコマンドラインツール）を実行すると、日本語プロンプトが文字化けして対話入力が機能しないという問題が発生しました。この種の「環境固有の落とし穴」を `feedback_android_build.md` に記録し、次回から同じ問題を回避できるようにしています。

```
記録例:
  JDKツール（keytool等）はWindows+bash環境で文字化けする
  → 全パラメーターをコマンドラインに指定する非対話モードで実行する
```

## 6. まとめ

この開発手法の核心は **「AIを使いこなすのではなく、AIと正しく役割分担する」** ことです。

| 人間が担う役割 | AIが担う役割 |
|---|---|
| 何を作るかを決める（仕様・スコープ） | 仕様に基づいてコードを生成する |
| 技術選定の最終判断をする | 選択肢の調査・比較表の作成 |
| コードをレビューする | 大量のコードを高速に書く |
| 実機で動作を確認する | ビルドエラーの原因究明と修正 |
| ルールを承認・更新する | ルールに従って一貫したコードを書く |

AIは「優秀だが指示がないと迷子になる」存在です。仕様書・ルール・チェックリストといった「地図」を整備することで、AIは最大のパフォーマンスを発揮します。逆に、地図なしで丸投げすると、速くは進めますが意図した方向に進んでいる保証がなくなります。

**「仕様を先に書く手間を惜しまない」** ことが、AI協働開発を成功させる最大のポイントです。
